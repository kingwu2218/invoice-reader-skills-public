# Core 0.3.4: terminal amount dash processing

This is a deterministic processor evaluation of invented JSON transcription, with no PDF reading or LLM call. It does not establish model or handwriting accuracy.

The same fixture is processed under three explicit conventions. `unknown` keeps the printed string and flags its ambiguous meaning; `end-mark` produces a positive number; `negative` produces a negative number. Unknown amounts are excluded from arithmetic. Converted standard amounts remain flagged with the original notation, and Run info records the selected convention. Custom observations remain unchanged.

Total: **51 / 51 configured workbook checks**, excluding correct blanks. These include arithmetic status, source pages and observation statuses alongside amounts. The fixed references cover an invoice total, cheque amount, line-item amounts, statement amounts and custom values. The executable matrix uses the shared workbook scorer and records script/input/reference hashes; the JSON is supplied test input, not model-produced raw evidence.

Unit tests also verify that malformed numbers, multiple/conflicting signs and unsupported dash forms are not repaired; a batch convention cannot convert quantities or override fields marked unclear. Source JSON and custom values remain unchanged. All **108 unit/regression tests** passed; generated-package drift/link checks and Codex skill validation passed.

The implementation intentionally does not convert every terminal dash to a positive number. Only a convention confirmed by the user for the selected documents may be applied; otherwise processing continues with flagged text. Mixed conventions require separate batches. This resolves the reusable interpretation mechanism without changing the frozen private reference, retroactively improving the old 18 / 19 score, or claiming a new private result.
